Ты проверяешь, что изменения в рабочем дереве не сломали тулчейн и команды репозитория.
Аргументы: `$ARGUMENTS` — база сравнения, по умолчанию `origin/main`.

Это лёгкая проверка, а не ревью. Соответствие issue, инварианты архитектуры, поиск багов
и смеллов — не твоя задача, для этого есть `/review-pr`. Ты работаешь по рабочему дереву,
а не по PR: ни `gh`, ни `gh pr checkout`, ни отдельный worktree под ревью здесь не нужны.
Ты запускаешь то, что можно запустить, и докладываешь результат.

## Жёсткие правила роли

- **Ты ничего не чинишь в этом прогоне.** Результат — отчёт. Найдено красное — скажи об этом
  и предложи починить отдельно; не правь файлы и не делай `--fix` по ходу проверки.
- **Запускать, а не читать глазами.** Проверка, которую ты не запустил, — это `n/a`, а не `ok`.
  Формулировки «выглядит корректно», «синтаксис в порядке», «должно работать» без вывода
  команды запрещены.
- **Ничего разрушающего, интерактивного и долгоживущего.** Полный список — в шаге 4.
  Сомневаешься, разрушающая ли цель, — не запускай её, поставь `n/a` и скажи почему.
- **Только затронутые группы.** Группа не задета изменениями — её проверки не запускаются
  вовсе и идут в отчёт как `n/a`. Гонять весь тулчейн ради правки в `README.md` — трата
  минут без единого возможного вывода.

## Шаг 1. Что изменилось

```bash
git status -sb
BASE=$(git merge-base "${1:-origin/main}" HEAD)
git diff --name-only "$BASE"                 # закоммиченное и правки в рабочем дереве
git ls-files --others --exclude-standard     # новые неотслеживаемые файлы
```

`git diff` без второй ревизии берёт рабочее дерево целиком, вместе с незакоммиченным, —
именно это и нужно проверять. Список пуст → скажи, что проверять нечего, и остановись.

## Шаг 2. Группы

Разложи файлы по двум группам. Файл может попасть в обе.

| Изменилось | Группа |
| --- | --- |
| `src/**/*.ts`, `test/**/*.ts` | тулчейн |
| `tsconfig.json`, `.mocharc.json`, `.eslintrc.js`, `.eslintignore`, `.prettierrc.js`, `.prettierignore` | тулчейн |
| `package.json` (зависимости), `package-lock.json` | тулчейн |
| `package.json` (блок `scripts`) | обе |
| `Makefile`, `scripts/*.sh`, `.husky/*` | команды |
| `Dockerfile`, `docker-compose.*.yml`, `migrate.json` | обе |
| `*.md`, `docs/**`, `.claude/**` | ни одна |

`package.json` делится по содержанию правки: тронуты `dependencies`/`devDependencies` —
это тулчейн, тронут блок `scripts` — ещё и команды. Посмотри диф файла, а не только имя.

## Шаг 3. Тулчейн

Node на хосте нет и запускать его напрямую нельзя: всё идёт через цели `Makefile`
в одноразовом контейнере. Контейнеру нужны поднятая база (сеть приложения объявлена внешней
и принадлежит проекту базы) и `.env` рядом с рабочим деревом.

```bash
make db-up
ls .env
```

`make db-up` поднимает общую базу и ничего в ней не стирает. `.env` нет → остановись
на этой группе и скажи, что нужен `make worktree-init`; сам его не запускай — он занимает
слот из пула токенов, а вернуть слот придётся вручную.

### Пересборка образа

```bash
make rebuild   # если изменены package.json, package-lock.json, .eslintrc.js,
               # .prettierrc.js, .mocharc.json или Dockerfile
```

Одноразовый контейнер берёт готовый образ и пересобирает его сам только когда образа нет
вовсе. Томами монтируются лишь `src`, `test`, `tsconfig.json` и `migrate.json` — `node_modules`
и конфиги линтера, форматтера и mocha живут в образе. Без `make rebuild` ты проверишь новый
код старыми зависимостями и старым конфигом и получишь зелёный результат, который ничего
не значит. `tsconfig.json` смонтирован, ради него пересобирать не нужно.

### Что запускать

```bash
make build
make test

TS=<изменённые .ts из шага 1>
[ -n "$TS" ] && make lint files="$TS"
[ -n "$TS" ] && make format-check files="$TS"
```

Проверка `[ -n "$TS" ]` обязательна: без `files` обе цели проверяют весь репозиторий, и ты
получишь унаследованные замечания вместо внесённых. В `files` кладутся **только `.ts`**:
`.prettierrc.js` жёстко задаёт `parser: "typescript"`, и на `.md`, `.json` или `.ftl`
prettier падает разбором. Это дефект конфигурации репозитория, а не твоего изменения;
в отчёт его не пиши.

Исключение — **изменён сам конфиг проверки**. Правка `.eslintrc.js` действует на весь код,
а не на изменённые файлы, поэтому такую цель гоняй без `files`, по всему репозиторию:
`.eslintrc.js` или `.eslintignore` → `make lint`, `.prettierrc.js` или `.prettierignore` →
`make format-check`, `.mocharc.json` → `make test`. Красное здесь почти наверняка означает,
что новый конфиг задел код, которого правка не касалась.

Что чем закрывается: `tsconfig.json` и любой `.ts` — `make build`; `.mocharc.json`
и `test/**` — `make test`; зависимости и `Dockerfile` — `make rebuild` плюс `make build`
и `make test`.

## Шаг 4. Команды

Здесь проверяется не текст, а поведение: цель раскрывается, скрипт разбирается, справка
печатается. Запускать по-настоящему можно только то, что ничего не меняет.

### Никогда не запускать по-настоящему

`make db-reset`, `make db-down` — разрушающие и общие для всех рабочих деревьев.
`make up`, `make app-up`, `make restart`, `make app-down`, `make logs` — поднимают или гасят
приложение и продлевают аренду токена. `make shell`, `make psql` — интерактивные.
`make migrate`, `make migrate-create` — меняют общую базу и репозиторий.
`make worktree-init`, `make token-acquire`, `make token-renew`, `make token-release`,
`make token-add` и соответствующие подкоманды `scripts/bot-token.sh` — трогают пул токенов
и `.env`. `scripts/db-reset.sh`, `scripts/worktree-init.sh` — напрямую тоже нет.

Каждая невыполненная цель попадает в отчёт строкой «не запускалось» с причиной — молчать
о ней нельзя.

### Makefile

```bash
make help
make help | grep -w '<изменённая цель>'
make -n <изменённая цель>
```

`make -n` печатает рецепт, не выполняя его, — это и есть проверка раскрытия переменных
(`DC_APP_RUN`, `FILES`, `RENEW_TOKEN`) без побочных эффектов. Единственное исключение GNU make —
строки с `$(MAKE)`: их он выполняет и под `-n`, но передаёт `-n` через `MAKEFLAGS`, поэтому
вложенный make тоже только печатает. Рецепт `db-reset` — `@scripts/db-reset.sh`, без `$(MAKE)`,
так что `make -n db-reset` безопасен и ничего не сотрёт.

Смотри в выводе `make -n`: подставились ли значения переменных, не осталось ли пустых
аргументов, не склеился ли многострочный `files` в одну команду.

Для новой или переименованной цели проверь заодно, без команд:

- у цели есть комментарий `## описание` — иначе она не появится в `make help`;
- имя добавлено в `.PHONY` — иначе цель сломается об одноимённый файл;
- обязательный параметр отвергается в самом рецепте (образец — `migrate-create` и `token-add`).

### Скрипты

```bash
sh -n scripts/<файл>.sh
```

Если изменено тело скрипта, а не только комментарии, прогони разбор ещё и dash'ем:

```bash
docker run --rm -v "$PWD":/app -w /app node:24-bookworm-slim sh -n scripts/<файл>.sh
```

Скрипты объявлены как `#!/usr/bin/env sh`, но на macOS `/bin/sh` — это bash в POSIX-режиме:
он пропускает bash-измы, которые упадут на dash в Linux-окружении. Разбор в контейнере ловит
именно их. Образ здесь нужен только как источник dash (`/bin/sh` в Debian), с версией Node
он не связан — подойдёт любой образ на Debian, уже лежащий на машине.

Подкоманды, которые ничего не меняют, запусти по-настоящему:

```bash
make token-status
scripts/bot-token.sh          # без аргументов печатает usage и выходит с кодом 1
```

Код выхода 1 у `usage` — ожидаемое поведение, а не падение.

### Скрипты npm

`build` и `test` уже закрыты шагом 3. `dev`, `start`, `start:prod` — долгоживущие, не запускай:
проверь только, что путь из скрипта существует (`main` в `package.json` указывает
на `build/app.js`, который появляется после `make build`). `migrate` и `prepare` не запускай
вовсе — первый меняет общую базу, второй переустанавливает хуки husky.

## Шаг 5. Базлайн — только если что-то красное

Красное в тулчейне само по себе ничего не значит: часть проверок может быть красной и
на базовой ветке. Прогони **только упавшую** команду на базе и сравни.

```bash
git worktree add <временный путь> origin/main
cp .env <временный путь>/.env
# та же одна команда в этом дереве
git worktree remove --force <временный путь>
```

`.env` копируется, а не создаётся через `make worktree-init`: тот занял бы слот пула токенов,
а одноразовым контейнерам `build`/`test`/`lint` бот не нужен и токен не читается. Имя проекта
Compose берёт из имени каталога, поэтому временное дерево не мешает основному.

Для группы «команды» базлайн не нужен: ошибка разбора в `sh -n` или незаданная переменная
в `make -n` однозначны сами по себе.

## Шаг 6. Отчёт

Выведи в сессию ровно в таком виде. Никуда не публикуй: это локальная проверка.

```
## Проверка изменений — база <sha> · файлов: <N>

**Итог:** ЗЕЛЕНО | КРАСНО | ЧАСТИЧНО

### Тулчейн — <затронут: что изменилось / не затронут>
rebuild: сделан/не нужен · build: ok/fail/n-a · test: ok/fail/n-a · lint: ok/fail/n-a · format-check: ok/fail/n-a

### Команды — <затронуты: что изменилось / не затронуты>
make help: ok/fail/n-a
make -n <цель>: ok/fail — <что показало раскрытие>
sh -n <скрипт>: ok/fail (+ dash: ok/fail/n-a)
<запущенная подкоманда>: ok/fail
Не запускалось: <цель/скрипт> — <причина>

### Красное
- <команда> — <первая значимая строка ошибки> [внесено этим изменением | было и на базе]

### Итог
<1–2 предложения: можно коммитить, или что именно чинить>
```

Правила итога:

- **ЗЕЛЕНО** — всё запущенное прошло. Пустые группы этому не мешают.
- **КРАСНО** — есть проверка, красная сейчас и зелёная на базе, либо любая ошибка
  в группе «команды».
- **ЧАСТИЧНО** — что-то не удалось запустить (Docker не работает, нет `.env`), либо всё
  красное унаследовано с базы. Скажи прямо, что именно осталось непроверенным.
