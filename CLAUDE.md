# CLAUDE.md

Telegram-бот (grammY + DI на inversify + PostgreSQL). Полная архитектура и проверенные рантайм-трассировки — в **`docs/architecture.md`** и **`docs/flows.md`**; прочитайте их перед нетривиальными изменениями. Оба документа получены построчным глубоким аудитом именно этой кодовой базы и описывают реальные баги, а не только задуманный дизайн. Этот файл покрывает лишь то, что нужно сессии, чтобы действовать безопасно, и не повторяет их содержимое.

## Правила ведения работы

- **Вся документация и все issues в этом репозитории ведутся на русском языке.** Это относится к `CLAUDE.md`, ко всему в `docs/`, к любым новым документам и к issues — заголовку, описанию и комментариям. Названия файлов, путей, классов, методов, переменных окружения, команд и прочие идентификаторы кода остаются в оригинальном виде — переводится текст, а не код. Если документ появляется на английском, его нужно перевести, а не оставлять как есть.
- **Любые изменения вносятся только через отдельную ветку и Pull Request.** Прямые коммиты и пуши в `main`/`master` не делаются никогда — ни для кода, ни для документации, ни для «мелких правок». Порядок: создать ветку от актуального `main` (`feat/…`, `fix/…`, `chore/…`, `docs/…`), закоммитить изменения туда, запушить и открыть PR. Одна ветка/PR — одна логически цельная задача; не смешивайте в одном PR несвязанные изменения.
- **Параллельные сессии работают каждая в своём git worktree, а не в одном общем дереве.** В репозитории одновременно ведётся несколько агентских сессий, а `git checkout` в общем рабочем дереве меняет HEAD сразу для всех — из-за этого коммит уходит в чужую ветку, и это уже случалось. Заводите под задачу отдельный worktree (`git worktree add <путь> -b <ветка> origin/main`); основное рабочее дерево остаётся за той сессией, которая уже в нём работает. Перед `git add`/`git commit` всё равно проверяйте `git status -sb`: ветка, созданная в начале сессии, могла смениться. Закончив, убирайте дерево — `git worktree remove <путь>`, затем `git worktree prune`.
    - `.env` в новое дерево не попадает (он в `.gitignore`) — скопируйте его из основного рабочего дерева.
    - **База общая, приложение — своё в каждом дереве.** Полный стек (`docker compose up --build`) поднимается только из основного дерева: имя проекта задано в `docker-compose.yml` как `telegram-bot`, а данные БД лежат в `./tmp/pgsql`, поэтому второй полный запуск либо подменит чужие контейнеры, либо создаст вторую, пустую базу на уже занятом `DATABASE_PORT`. В worktree допишите в `.env` свои `COMPOSE_PROJECT_NAME`, `APP_DATABASE_HOST=host.docker.internal` и `APP_DATABASE_PORT`, равный `DATABASE_PORT` основного дерева, и поднимайте один сервис: `docker compose up --build --no-deps app`.
    - **`BOT_TOKEN` берётся из общего пула, по одному на дерево.** `scripts/bot-token.sh acquire` занимает свободный слот и записывает токен в `.env` текущего дерева, `renew` продлевает аренду (вызывайте перед запуском бота и перед долгими действиями), `release` освобождает слот по окончании работы. Аренда привязана к пути рабочего дерева и протухает по TTL, поэтому удалённое или брошенное дерево освобождает токен само. Запускать бота без аренды нельзя: два процесса на long polling с одним токеном получают от Telegram 409 Conflict и растаскивают апдейты друг у друга.

## Приоритеты проекта

- **Сохранение форматов шрифтов (`src/domain/font-convertor/`) — и есть настоящий смысл проекта**: конвертация и сохранение файлов шрифтов между максимально возможным числом форматов. Telegram (`src/infrastructure/bot/`), домен `User`, `BulkMessagesCommand` и миграции Postgres существуют, чтобы обслуживать этот Telegram-фронтенд; они не являются самостоятельными фичами. По умолчанию считайте корректность и покрытие `font-convertor` самой ценной областью, а всё остальное — обслуживающей инфраструктурой.
- **Сервис улучшается инкрементально, по одной области за раз, а не переписывается.** Запланированные области (без фиксированного порядка): слои и границы модулей, конфиг, логгер, интеграция с Telegram, миграции, зависимости, Docker и сама логика сохранения шрифтов. Не предлагайте и не начинайте большой многообластной переписыванием без запроса — ограничивайте изменения тем, о чём реально просят в конкретной сессии.
- **Переусложнение в этой кодовой базе реально, и его следует называть прямо, а не тихо обходить.** Слои логгера и конфига несут больше косвенности (перебиндивание через `Proxy`, декораторы свойств в стиле service locator, читающие из глобального контейнера, два бэкенда логирования), чем требует реальный масштаб приложения — один процесс, один источник конфигурации; конкретику см. в `docs/architecture.md` §17/§19. При работе с любым из них нормально сказать об этом и предложить упрощение, а не только расширять существующий паттерн.

## Команды

- **Единственный способ запуска — Docker; на хосте ничего, кроме Docker, не требуется.** `docker compose up --build` поднимает `pgsql`, затем `app`, который накатывает миграции и стартует бота в watch-режиме с примонтированным `./src`. Среда только для разработки — production-конфигурации в репозитории нет. Подробности в `README.md` и `docs/architecture.md` §15. Из worktree стек поднимается иначе — см. правило про worktree выше.
- `npm run migrate -- up` — применить миграции (`node-pg-migrate`, конфигурация в `migrate.json`). Действие (`up`/`down`/`create`) обязательно передаётся аргументом — голый `npm run migrate` печатает usage и выходит с кодом 1.
- `npm run build` — `tsc` + `tsc-alias` (переписывает алиас `app/*` в относительные пути для `build/`).
- `npm run dev` — запуск без сборки: `node --watch` + `ts-node` + `tsconfig-paths` по `src/app.ts`.
- `npm start` / `npm run start:prod` — запускает `build/app.js`, тот же файл, на который указывает `package.json#main`. **Сейчас этот путь нерабочий:** `tsc` не копирует `.ftl`-локали в `build/`, поэтому запуск из `build/` падает с `ENOENT` (`docs/architecture.md` §18, issue #19).
- `npm test` — mocha по `test/**/*.spec.ts`. **Во всём репозитории фактически один настоящий тест** (`test/services/message-broker/slot-manager/slot-manager.spec.ts`, проверяющий `SlotManager` в изоляции), а `test/bootstrap.ts` (загружаемый тестовым скриптом) пуст. **Сейчас прогон красный из-за багов в самом spec-файле, а не в `SlotManager`** (подробности в `docs/architecture.md` §14) — это известное состояние, не считайте его регрессией своих изменений. И в любом случае не считайте `npm test` осмысленным покрытием того, что вы изменили, — проверяйте вручную.

## Конвенции архитектуры (кратко — полностью в `docs/architecture.md`)

- **Только алиас импортов:** каждый внутренний импорт использует `app/*` (→ `src/*`), никаких относительных путей. Правило ESLint `no-restricted-imports` полностью запрещает относительные импорты (`.eslintrc.js`) — относительный импорт упадёт на линтере, а не просто «будет выглядеть неправильно». Файлы миграций — единственное намеренное исключение.
- **DI собирается вручную, без автообнаружения.** Новые классы с `@injectable()` (команды, middleware, фильтры, сервисы, conversations) не делают ничего, пока вы не добавите соответствующую строку `this.bind<T>(Symbol).to(Class)` в `src/infrastructure/container/container.ts` плюс символ в `src/infrastructure/container/symbols/`. Ничто не предупредит вас, если вы забудете, — класс просто молча никогда не выполнится.
- **Слои:** `domain/` — бизнес-логика и порты, не зависящие от фреймворков; `infrastructure/` — адаптеры (Postgres, grammY, логгеры, конфиг). Держите новый доменный код свободным от импортов `grammy`/`postgres`/`pino` — им место в `infrastructure/`.
- **Именование файлов:** текущая конвенция — kebab-case (`fill-user-to-context.middleware.ts`); горстка старых файлов в `infrastructure` использует dot-case (`pgsql.decorator.ts`, `abstract.logger.ts`) как остатки до рефакторинга. Для всего нового используйте kebab-case и не тиражируйте старый стиль.
- **Ошибки:** для доменных ошибок всегда наследуйтесь от `RuntimeError` (`src/common/errors.ts`), с фабрикой `static byX(...)` по существующему образцу в файлах `*.errors.ts`. **Не вызывайте унаследованный `RuntimeError.byError()`** на подклассе в расчёте получить экземпляр этого подкласса — он всегда бросает изнутри себя обычный `RuntimeError` вместо возврата (реальный, сейчас дремлющий баг базового класса; см. `docs/architecture.md` §17). Если нужна обёртка с типом подкласса, напишите собственную фабрику подкласса, а не полагайтесь на унаследованную.

## Инварианты системы — не ломать

- **Обрабатываются только приватные чаты.** `IsPrivateChatFilter` отбрасывает всё остальное после стадии middleware/сессии/upsert'а пользователя. Если вы добавляете поддержку групповых чатов, вам придётся также пересмотреть групповые рейт-лимиты в `Planner` (они настроены, но сейчас недостижимы) и белый список `TELEGRAM_NO_GROUP_RATE_LIMIT_SET` в `TelegramCallApiMiddleware`, который применяется только к группам.
- **`ctx.api` — новый объект на каждый входящий апдейт** (grammY создаёт новый экземпляр `Api` для каждого апдейта — проверено по точной зафиксированной версии grammY, `1.10.1`). Никогда не предполагайте, что состояние, выставленное на `ctx.api` (или его `.raw`), переживёт апдейт, и никогда не предполагайте, что `ctx.api === bot.grammy.api` — это разные объекты. Код, которому нужно отправлять сообщения вне обработки конкретного апдейта (фоновые задачи, массовые рассылки), обязан вызывать через `bot.grammy.api` **и вручную делать `planner.push(...)`**, чтобы получить ограничение скорости, — см. существующий (пусть и небезопасный в остальном) паттерн в `BulkMessagesCommand`.
- **`ctx.session` бросает исключение при обращении, если отсутствует `ctx.from` или `ctx.chat`** (например, посты в канале) — это собственное поведение grammY при текущей реализации `getSessionKey` в `session.helper.ts`, а не баг, который надо «чинить» локально, не меняя `getSessionKey`. Любой новый middleware, поставленный до `FillUserToContextMiddleware` и безусловно трогающий `ctx.session`, уронит пайплайн для таких апдейтов — ровно так, как это сейчас делает `RequestLogMiddleware`. Если нужно аккуратно обрабатывать апдейты без `from`/`chat`, защищайте само обращение к `ctx.session`, а не копируйте паттерн `if (!ctx.from)` из `FillUserToContextMiddleware`: этот паттерн (согласно `docs/flows.md`, Поток 3) сегодня вообще не достигается.
- **Ограничение скорости обеспечивается целиком связкой `Planner`/`SlotManager`, а не логикой повторов/банов в `Broker`** — последняя, весьма вероятно, является мёртвым кодом в рантайме (точная причина через цепочку Promise — в `docs/flows.md`, Поток 4). Не стройте новые фичи в расчёте на то, что бот автоматически отступает при HTTP 429; сейчас он этого не делает.
- **i18n однолокальна (`"ru"`) по захардкоженному дизайну** (`localeNegotiator` в `Bot.setupFlavor`). Добавление нового файла `.ftl` само по себе не делает его достижимым — нужно ещё изменить негоциатор, чтобы он реально выбирал локаль на пользователя.
- **Миграции append-only.** Никогда не редактируйте уже применённый файл миграции в `src/infrastructure/database/migrations/` — добавляйте новый (скаффолдинг `node-pg-migrate`, шаблон в `migrations/common/template.ts`). Существующая миграция `users.id` int→bigint появилась именно потому, что ранняя миграция задала неверный тип колонки; не повторяйте это ручной правкой истории.

## Неочевидные детали реализации, которые стоит знать перед правкой связанного кода

(Полный список с точной механикой — в `docs/architecture.md` §17 и `docs/flows.md`.)

- `TelegramCallApiMiddleware` перехватывает исходящие вызовы Telegram через `Proxy` на `ctx.api.raw`, направляя всё, у чего payload — простой объект с `chat_id`, в очередь `Planner`. Payload'ы, не являющиеся простыми объектами (например, multipart-загрузки файлов), полностью минуют очередь — непроверенная территория, если вы добавите фичу с загрузкой файлов.
- `FileHelper.createDirectoriesByDate` раскладывает по дню **недели** (`dayjs().day()`), а не по дню месяца — путь выглядит как `YYYY/M/D`, но означает не то. Не полагайтесь на него для реальной календарной раскладки, не исправив предварительно путаницу `.day()`/`.date()`.
- Сгенерированные файлы шрифтов пользователю никогда не загружаются — существующий код отвечает локальным путём на сервере в виде текста. Если вы будете делать настоящую отправку файлов, файл нужно именно прикрепить (например, `InputFile`), а не следовать существующему паттерну.
- Proxy логгера Postgres (`Container.setupInfrastructureLogger`) заново применяет `setLevels()` и заново разрешает дочерний логгер запроса при **каждом** доступе к свойству, а не один раз — это намеренно (так работает корреляция запросов на `AsyncLocalStorage`), но означает, что вызовы логгера не так дёшевы, как кажутся.

## Обращаться с особой осторожностью

- **`src/infrastructure/container/container.ts`** — центральная, поддерживаемая вручную проводка; пропущенный или неверно упорядоченный биндинг падает молча (без ошибки), а не громко.
- **`src/infrastructure/bot/middleware/mutation/telegram-call-api.middleware.ts`** и **`src/domain/planner/planner.ts`** / **`src/domain/broker/broker.ts`** — ядро ограничения скорости. Изменения здесь влияют на то, может ли бот получить бан от Telegram; проверяйте вручную на реальных рейт-лимитах, поскольку автоматического покрытия нет, а существующая логика повторов фактически не выполняется (см. инварианты выше).
- **`src/infrastructure/bot/command/bulk-messages/bulk-messages.command.ts`** — живая команда `/bulk_messages` без аутентификации, которая ставит в очередь до 300 000 исходящих сообщений на захардкоженные chat ID при вызове *любым* пользователем. Считайте её тем, что нужно удалить или закрыть авторизацией, а не расширять. Не берите её паттерн (ручной `bot.grammy.api` + `planner.push`) за образец для новых фич массовой рассылки, не добавив сначала настоящую авторизацию.
- **`.env.dist`** — содержит похожий на настоящий `BOT_TOKEN` открытым текстом. Никогда не коммитьте живой токен ни сюда, ни в любой другой отслеживаемый файл; считайте существующий в истории git скомпрометированным, если он когда-либо окажется настоящим.
- **Файлы миграций в `src/infrastructure/database/migrations/`** — append-only, см. инварианты выше.

## Стиль кода

- Prettier: отступ 4 пробела, строки до 140 символов, двойные кавычки, висячие запятые. Обеспечивается через Husky `pre-commit` (`lint-staged` → `eslint --fix`, затем `prettier --write`) — не обходите это с `--no-verify`.
- Никаких комментариев, объясняющих, *что* делает код; правильный ориентир — существующий стиль комментариев в этом репозитории (редкие, в основном на русском, объясняющие *почему* для неочевидных хаков вроде прокси в `TelegramCallApiMiddleware`), а не многословные doc-комментарии.
