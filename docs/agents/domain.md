# Домен-доки

Как агентским скиллам читать документацию этого репозитория.

## Что читать перед исследованием кода

1. **`docs/architecture.md` и `docs/flows.md`** — источник правды по устройству кода:
   слои, DI, пайплайн ограничения скорости, трассировки рантайма, инварианты. Читаются
   первыми и остаются главными документами репозитория.
2. **`CONTEXT.md`** в корне — глоссарий предметной области (форматы шрифтов и их
   конвертация). Только термины, без деталей реализации.
3. **`docs/adr/`** — записи о принятых решениях, относящиеся к области, которую вы правите.

`CONTEXT.md` и `docs/adr/` пока не существуют — это нормально. **Не сообщайте об их
отсутствии и не предлагайте создать их заранее.** Они создаются лениво: `CONTEXT.md` —
скиллом `domain-modeling` при разрешении первого термина, ADR — при первом решении, которое
трудно откатить, удивит будущего читателя и стало результатом настоящего выбора из
альтернатив. Задним числом ADR по уже принятым решениям не пишутся.

Структура — single-context: `CONTEXT.md` и `docs/adr/` в корне репозитория.

## Пользуйтесь словарём глоссария

Если ваш вывод называет доменное понятие (заголовок issue, предложение по рефакторингу,
имя теста), используйте термин так, как он определён в `CONTEXT.md`, не подменяя синонимами.
Понятия нет в глоссарии — это сигнал: либо вы придумываете язык, которого в проекте нет,
либо есть реальный пробел, и его стоит отметить для `domain-modeling`.

## Сообщайте о конфликтах с ADR

Если вывод противоречит существующему ADR, скажите об этом явно, а не переписывайте решение
молча: «Противоречит ADR-0007 (…), но пересмотреть стоит, потому что…».
