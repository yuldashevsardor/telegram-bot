# i18n

The supported locales are listed in `telegram/locale/locale.types.ts`: `LOCALES` and
`DEFAULT_LOCALE` (`ru`). The list is explicit because the locale comes from the file name,
and a typo would otherwise create a bundle for a language nobody is ever routed into. Name
parsing and bundle assembly are in `locale.ts`.

The `.ftl` are read from disk once per process, at the Fluent step of `Bot.setup()`
([`bot.md`](./bot.md)): `setupFlavor()` calls `createFluent(path.dirname(__dirname))`, which
collects all of them under the subsystem directory of the running code — `src/telegram` in
development and `build/telegram` after a build. `__dirname` here is the `bot/` directory
inside it, while the `.ftl` lie next to the commands and the conversations, so the walk
starts one level up. The locale of each file is taken by `localeFromFilePath()` from the
`*.locale.<lang>.ftl` convention — the second to last name segment
(`start.conversation.locale.ru.ftl` → `ru`); an unknown locale gives `UnknownLocale`, a
locale without a single file `MissingLocaleBundle`. `isDefault: true` goes to exactly the
`DEFAULT_LOCALE` bundle: Fluent appends the default bundle to the tail of the lookup chain,
and on it a key missing from the user's locale returns text and not its own name.
`useIsolating` is off: by default Fluent wraps every placeable in invisible U+2068/U+2069,
while what travels through the placeables here is data that gets copied, and there are no
right-to-left locales.

Neither of those errors is caught, and neither is a failure of `addTranslation()` on a
broken `.ftl`: they pass through `Bot.setup()` and `Application.setup()` and bring the start
down ([`application.md`](./application.md)).

The locale of an update is `resolveLocale(ctx.from?.language_code)`: the region of the IETF
tag is dropped (`en-US` → `en`), an unknown language goes to `DEFAULT_LOCALE`. The user has
no stored language setting.

Fluent is put into the pipeline by `createFluentMiddleware()` — our own middleware instead
of `useFluent()` from `@grammyjs/fluent`. It is also what resolves the locale once per
update and binds `ctx.t` to it. The plugin puts `fluent`, `translate` and `t` into the
context with a single `Object.assign`, and the enumerable `fluent` field would travel whole
into the conversation op-log and into `sessions` ([`invariants.md`](./invariants.md)),
together with the parsed bundles, and come back an empty shell: the `Set` of bundles and the
`Map` of messages collapse into `{}` on serialization. The property name cannot be given to
the plugin, which is why it is replaced: the instance lies behind `ctx.getFluent()`, the
translation in `ctx.t`. Both are functions: the conversations plugin does not clone them but
restores them bound to the live context ([invariant](./invariants.md)), so inside a
conversation they work. `ctx.translate`, the plugin's second name for `ctx.t`, was not
carried over: it had no consumers.

Command descriptions are translated too: `Command.descriptionKey` is a key and not a text,
and `Bot.setupCommands()` calls `setMyCommands()` for every locale — first without
`language_code` (the fallback set, on `DEFAULT_LOCALE`), then once per remaining locale.
They are translated by the same `Fluent` instance that stands in the pipeline:
`setupFlavor()` returns it upwards, which is why the Fluent step of `Bot.setup()` comes
before the commands are registered ([`bot.md`](./bot.md)).

A key name starts with the module that owns it (`start-command-description`,
`start-conversation-welcome`) — [invariant](./invariants.md): all the `.ftl` of one locale
are glued into a single flat bundle, and the keys of different modules live in a shared
namespace. `test/telegram/locale.spec.ts` catches both a divergence of the key sets between
locales (which does not fail by itself but silently hands the user a foreign language
through the fallback into the default bundle) and a key the code asks for that no `.ftl`
declares (Fluent would return `{key}`).

The list of formats in the welcome (`start-conversation-welcome`) is written neither into
the `.ftl` nor as a string in the code: `StartConversation` substitutes it from
`ConvertorFactory.getSupportedExtensions()` ([`font-convertor.md`](./font-convertor.md)) —
what is promised to the user changes together with the pair matrix.

The `.ftl` are put into `build/` by a separate step of `npm run build`
(`cpy "src/**/*.ftl" build`): `tsc` moves only the result of compiling the `.ts`. The step
and the path from `__dirname` work only as a pair — the copying without it would still read
the locales from `src/`, and the path without the copying would run into an empty
`build/telegram`. The development container is run through `npm run dev`, from the sources.
