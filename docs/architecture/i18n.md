# i18n

The supported locales are listed in `telegram/locale/locale.types.ts`: `LOCALES` and
`DEFAULT_LOCALE` (`ru`). The list is explicit because the locale comes from the file name.
Otherwise a typo in a name would create a bundle for a language nobody is ever routed into. Name
parsing and bundle assembly are in `locale.ts`.

The `.ftl` are read from disk once per process, at the Fluent step of `Bot.setup()`
([`bot.md`](./bot.md)). `setupFlavor()` calls `createFluent(path.dirname(__dirname))`, which
collects every `.ftl` under the subsystem directory of the running code: `src/telegram` in
development, `build/telegram` after a build. `__dirname` is the `bot/` directory inside it, while
the `.ftl` lie next to the commands and the conversations, so the walk starts one level up.

`localeFromFilePath()` takes the locale of each file from the `*.locale.<lang>.ftl` convention:
the second to last segment of the name (`start.conversation.locale.ru.ftl` → `ru`). An unknown
locale gives `UnknownLocale`, a locale without a single file `MissingLocaleBundle`.

`isDefault: true` goes to exactly the `DEFAULT_LOCALE` bundle. Fluent appends the default bundle
to the tail of the lookup chain, and on it a key missing from the user's locale returns text, not
its own name.

`useIsolating` is off. By default Fluent wraps every placeable in invisible U+2068/U+2069. Here the
placeables carry data that gets copied, and there are no right-to-left locales.

`UnknownLocale`, `MissingLocaleBundle` and a failure of `addTranslation()` on a broken `.ftl` are
not caught. They pass through `Bot.setup()` and `Application.setup()` and bring the start down
([`application.md`](./application.md)).

The locale of an update is `ctx.from?.language_code`, handed to `fluent.withLocale()` as is; with
no `language_code` it is `DEFAULT_LOCALE`. Fluent negotiates the IETF tag with `@fluent/langneg`
(`en-US` → the `en` bundle, case ignored). A language without a bundle matches nothing, and the
user gets the text of the default bundle at the tail of the chain. So does a supported language in
a tag langneg cannot parse (`en-001`, `en-US-x-foo`): its `localeRe` takes a two-letter region
only and no extensions. The user has no stored language setting.

`createFluentMiddleware()` puts Fluent into the pipeline: our own middleware instead of
`useFluent()` from `@grammyjs/fluent`. It also binds `ctx.t` to the locale of the update. The
plugin was replaced because of its `fluent` field:

- The plugin puts `fluent`, `translate` and `t` into the context with a single `Object.assign`.
- The enumerable `fluent` field would travel whole into the conversation op-log and into
  `sessions` ([`invariants.md`](./invariants.md)), together with the parsed bundles.
- It would come back an empty shell: the `Set` of bundles and the `Map` of messages collapse into
  `{}` on serialization.
- The property name cannot be given to the plugin.

So the instance lies behind `ctx.getFluent()`, and the translation in `ctx.t`. Both are
functions: the conversations plugin does not clone them but restores them bound to the live
context ([invariant](./invariants.md)), so they work inside a conversation. `ctx.translate`, the
second name of the plugin for `ctx.t`, was not carried over: it had no consumers.

Command descriptions are translated too: `Command.descriptionKey` is a key, not a text.
`Bot.setupCommands()` calls `setMyCommands()` for every locale: first without `language_code`
(the fallback set, in `DEFAULT_LOCALE`), then once per remaining locale. The same `Fluent`
instance that stands in the pipeline translates them: `setupFlavor()` returns it upwards. That is
why the Fluent step of `Bot.setup()` comes before the commands are registered
([`bot.md`](./bot.md)).

A key name starts with the module that owns it (`start-command-description`,
`start-conversation-welcome`), [invariant](./invariants.md). All the `.ftl` of one locale are
glued into a single flat bundle, so the keys of different modules share one namespace.

`test/telegram/locale.spec.ts` catches two mistakes:

- The key sets of the locales diverge. That fails nothing by itself: the fallback into the default
  bundle silently hands the user a foreign language.
- The code asks for a key that no `.ftl` declares. Fluent would return `{key}`.

The list of formats in the welcome (`start-conversation-welcome`) is written neither into the
`.ftl` nor as a string in the code. `StartConversation` substitutes it from
`ConvertorFactory.getSupportedExtensions()` ([`font-convertor.md`](./font-convertor.md)), so what
the user is promised changes together with the pair matrix.

A separate step of `npm run build` puts the `.ftl` into `build/` (`cpy "src/**/*.ftl" build`):
`tsc` moves only the result of compiling the `.ts`. The step and the path from `__dirname` work
only as a pair. With the copies but a path from the working directory, the built application
would still read the locales from `src/`. With the path but no copies, it would find no `.ftl` in
`build/telegram`. The development container runs `npm run dev`, from the sources.
