# Очередь исходящих (TaskQueue / Partition / Runner)

Ограничивает темп исходящих вызовов Telegram. О Telegram знает минимум: работает с
задачами по произвольному ключу; телеграмное — `telegram-error.ts` в домене (коды, по
которым `Runner` опознаёт 429) и `TelegramLimitResolver` с `isGroupChat` в
инфраструктуре (отрицательный chat ID — группа).

```
push(task, priority) → Partition ключа (заводится по первой задаче; лимит ключа
                        один раз спрашивается у LimitResolver) + индекс keysByPriority
pull()               → 0. снять с головы idleKeys партиции, которые пусты и остыли
                       1. null при паузе после 429, пустой очереди или занятом общем лимите
                       2. HIGH → MEDIUM → LOW; внутри приоритета — первый ключ, чей лимит остыл
                       3. Partition.take() отдаёт голову корзины и резервирует лимит ключа,
                          TaskQueue резервирует общий лимит
Runner               → цикл на setTimeout: pull(), выполнить callback, не дожидаясь,
                       следующая итерация через setTimeout(0); при пустом pull — случайный
                       сон в [RUNNER_SLEEP_INTERVAL_MIN, ..._MAX], почему — ниже
```

- **`TaskQueue`**: ключ → партиция, индекс приоритетов `keysByPriority` (`Set` хранит
  порядок вставки) и `idleKeys`; сверх них — общий `RateLimit` и метка паузы, они и дают
  оба `null` из пункта 1 схемы. Порядок не строгий FIFO: ключ под лимитом
  пропускается. Отдавший ключ переставляется в хвост `Set`, иначе при дефолтных
  лимитах обслуживались бы только первые десять ключей. Приоритет глобальный.
- **`Partition`**: три корзины по приоритетам, внутри корзины FIFO; свой `RateLimit`.
- **`RateLimit`**: один слот с остыванием `interval / number`, не token bucket.
  `reserve()` при занятом слоте бросает `RateLimitIsBusy`. `number = 0` даёт
  бесконечное остывание, конфиг это не проверяет.
- **Жизнь партиции**: удаляется, когда пуста и остыла. Пустоту очередь видит сразу
  после `take()`, в `pullByPriority`, и кладёт ключ в `idleKeys`; остывание проверяет
  следующий `pull()`, обход обрывается на первой остывающей, не больше
  `REMOVED_PARTITIONS_PER_PULL` (100) за вызов. Удалять по одной пустоте нельзя: пока
  идёт остывание, партиция и есть лимит ключа.
- **Ошибки**: `Runner.handleTask` ловит отказ `callback` и зовёт два метода:
  `handleError` пишет `error` и при 429 ставит `TaskQueue.ban()`, `retryTask` возвращает
  задачу с `priorityOnError`, увеличивая её `retryCount`; повторов ровно
  `RUNNER_MAX_RETRIES`, дальше задача отбрасывается — но `error`-ом в логе, не молча.
  `ban()` считает миллисекунды, а Telegram присылает `retry_after` в секундах, поэтому
  `Runner` умножает на 1000 (нечитаемый `retry_after` → `DEFAULT_RETRY_AFTER_SECONDS`):
  без множителя пауза после 429 вышла бы в тысячу раз короче требуемой. Вызывающая сторона
  видит первый отказ, а не итог повторов: иначе `ctx.reply()` висел бы всю паузу.
  Опознание 429 и повтор у `Runner` автотестами не покрыты ([`testing.md`](./testing.md)),
  проверены вручную; сама пауза очереди закреплена спекой `TaskQueue`.

Лимиты по умолчанию (`.env.dist`, рекомендации Telegram): common 30/1 с, private
3/1 с, group 20/60 с. Сон цикла — 10–1000 мс, выбирается случайно на каждой пустой
итерации: ровный шаг раз за разом попадал бы в одну и ту же точку окна остывания.

## Путь исходящего вызова

Любой `ctx.api.*` (включая `ctx.reply`) во время обработки апдейта идёт так:

1. Метод `Api` grammY собирает payload и зовёт `ctx.api.raw[method](payload, signal)`; на
   `raw` стоит `Proxy` из `TelegramCallApiMiddleware` ([`bot.md`](./bot.md)), он отдаёт
   `callApi`.
2. `callApi` либо зовёт сохранённый `originRaw` напрямую (условия обхода —
   [`bot.md`](./bot.md)), либо создаёт Promise, строит `callback`, кладёт задачу в очередь
   и отдаёт Promise вызывающей стороне — то есть та получает его до того, как вызов
   сделан, и ждёт всё время, пока задача лежит в очереди.
3. Задачу отдаёт очередной `pull()` цикла `Runner.handleTasks` (схема выше), `handleTask`
   делает `await task.callback()`.
4. `callback` дожидается реального вызова и разрешает Promise: успех — `messageResolve`,
   отказ — `messageReject` и повторный `throw`. Отказ нужен обеим сторонам: вызывающей —
   как отказ `ctx.reply()`, очереди — как вход в пункт «Ошибки» выше. Без `await` внутри
   `callback` наружу ушёл бы ещё не завершённый promise, и очередь отказа Telegram не
   увидела бы. Повтор берёт тот же `callback`, поэтому удачная вторая попытка сообщение
   пользователю отправит, но уже отклонённый Promise не изменит.
5. Дальше цепочка обрывается: ни один обработчик не отвечает пользователю на сбой
   отправки — отказ заканчивается логом ([`bot.md`](./bot.md)).
