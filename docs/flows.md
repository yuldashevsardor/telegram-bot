# Сквозные потоки

Этот документ трассирует фактическое рантайм-поведение системы — не только то, что код структурно выглядит делающим, но и то, что он делает при исполнении, включая точную семантику Promise/async и взаимодействие с нижележащим фреймворком grammY. Он является результатом второго, более глубокого прохода анализа поверх [`docs/architecture.md`](./architecture.md) и нацелен именно на проверку сделанных там утверждений против рантайм-поведения.

**Замечание о методологии:** несколько находок ниже зависят от того, как именно ведёт себя grammY изнутри (версия зафиксирована как `1.10.1` в `package-lock.json`), а не только от кода этого репозитория. Эти моменты проверялись по реальным исходникам grammY на теге `v1.10.1`, а не принимались на веру из общего знакомства с фреймворком, поскольку ошибочное допущение здесь дало бы неверное описание потока. Там, где это было важно, сказано явно.

Этот проход нашёл **четыре подтверждённых рантайм-бага, пропущенных первым (структурным) проходом**, — все они исправлены и в `docs/architecture.md`:

1. Отладочный код команд `/font_generator` и `/start` никогда фактически не отправляет пользователю сгенерированный файл шрифта — он отправляет текстовым сообщением локальный путь в файловой системе сервера.
2. Защита `if (!ctx.from)` в `FillUserToContextMiddleware` — недостижимый мёртвый код: пайплайн уже падает на один middleware раньше (`RequestLogMiddleware`) для любого апдейта без `ctx.from`, потому что session-middleware grammY бросает исключение при обращении к `ctx.session`, если его ключевая функция вернула `undefined`.
3. `FileHelper.createDirectoriesByDate` раскладывал временные файлы конвертации по **дню недели** (0–6), а не по дню месяца, поскольку вызывал `.day()` из dayjs вместо `.date()`. **Исправлено** в issue [#30](https://github.com/yuldashevsardor/telegram-bot/issues/30).
4. Трассировка точной цепочки Promise через `TelegramCallApiMiddleware` → `Broker` показывает, что логика перехвата-и-повтора и бана по 429 в `Broker` с высокой вероятностью **мертва в рантайме**: сработать она может только на синхронный throw, которого реальный вызов Telegram API практически никогда не даёт.

Каждый пункт разобран в соответствующем потоке ниже.

**Правила репозитория:** документация и issues ведутся на русском языке, а любые изменения вносятся только через отдельную ветку и Pull Request — прямые коммиты в `main`/`master` не делаются. Подробнее — в [`docs/architecture.md`](./architecture.md) и `CLAUDE.md`.

## 1. Старт процесса (bootstrap)

**Триггер:** запуск процесса (`node build/app.js`, то есть `npm start`/`npm run start:prod`).

**Последовательность:**
1. `src/app.ts` импортирует `reflect-metadata` (должно произойти до загрузки любого класса с декораторами inversify, иначе метаданных `@injectable()`/`@inject()` не будет).
2. `container.setup()` выполняется синхронно-по-порядку (полное дерево биндингов — в `docs/architecture.md` §4): `setupModules()` (биндит `Planner`, `Broker`, затем все биндинги из `setupBot()`) → `setupServices()` (стеки font-convertor и user) → `setupInfrastructure()` (`Config`, `Database`, затем `setupInfrastructureLogger()`).
   - Конструктор `Config` выполняет `dotenvExpand.expand(dotenv.config())` **в момент импорта модуля** (инструкция верхнего уровня в `config.ts`, а не внутри конструктора) — то есть `.env` реально загружается при первом импорте `config.ts` кем угодно, что на практике происходит очень рано (транзитивно почти каждый связанный в DI класс импортирует что-то, что импортирует `Config`).
   - Конструктор `Database` вызывает `postgres({...})`, который сразу открывает пул соединений — **это происходит во время `container.setup()`, ещё до того, как бот попытается обратиться к базе**, так что неверная конфигурация БД падает быстро, на старте, а не при первом запросе.
3. `container.get<Bot>(Modules.Bot.Bot)` разрешает синглтон `Bot`. Конструктор `Bot`: читает `@ConfigValue<BotSettings>("bot")` → если `settings.token` ложный, **синхронно бросает исключение** (`throw new Error("Bot token cannot be empty!")`) ещё до того, как `bootstrap()` дойдёт до `bot.run()`.
4. `await bot.run()`:
   - `await this.broker.run()` — **обратите внимание:** `Broker.run()` на самом деле синхронный (`public run(): void`), поэтому этот `await` — пустая обёртка вокруг синхронного вызова, он ничего не ждёт. Бросает исключение, если `Broker.isRun` уже `true` (защита от двойного старта; при нормальной загрузке недостижима).
     - Внутри `Broker.run()` выставляет `_isRun = true` и планирует `setTimeout(this.handleMessages.bind(this), 0)` — воркер исходящей очереди стартует на следующем тике, независимо от остального bootstrap.
   - `await this.setup()` — выполняет полную регистрацию пайплайна grammY (сессия → sequentialize → middleware → flavor/i18n → фильтры → conversations → команды). Что делает регистрация «команд» по сети — см. Поток 3. Именно здесь **`setupFlavor()`** собирает файлы `.ftl` с диска (см. Поток 8), а **`setupCommands()`** делает живой вызов `setMyCommands` к Telegram API.
   - `this.grammy.catch(this.handleError.bind(this))` — регистрирует обработчик ошибок верхнего уровня (что до него доходит — см. Поток 3).
   - `this.runner = run(this.grammy)` — запускает цикл long-polling из `@grammyjs/runner`. Это вызов «запустил и забыл»: `run()` начинает опрос в фоне и немедленно возвращает хендл, не дожидаясь завершения цикла опроса.
   - `this.isRun = true`, лог `"Bot is successfully started."` на уровне `info`.
   - **Если любой шаг в `try` бросает исключение** (например, `setup()` может упасть из-за сбоя сбора `.ftl` или из-за неудачного сетевого вызова `setMyCommands`): блок `catch` выполняет `this.broker.stop()`, затем `await this.handleError(error)` (лог `critical`) и **пробрасывает ошибку дальше**. `bootstrap()` реджектится, `bootstrap().catch(fail)` в `app.ts` печатает ошибку в `console.error` и завершает процесс с кодом 1 — старт, который не состоялся, не выглядит успешным для супервизора. `Bot.isRun` при этом остаётся `false`, runner не запущен.

**Изменения состояния:** DI-контейнер полностью заполнен и закрыт (`alreadySetup = true`); открыт один пул соединений Postgres; `Broker._isRun = true`; `Bot.isRun`/`isSetup = true` (при отсутствии ошибок).

**Обращения к хранилищу:** открыт пул соединений Postgres (запросов на этом этапе ещё нет).

**Внешние вызовы:** `grammy.api.setMyCommands(commands)` — один HTTP-вызов к Telegram, выполняется во время `setupCommands()` (часть `setup()` из шага 4).

**Обработка ошибок:** любой сбой старта завершает процесс с кодом 1. Исключение из конструктора `Bot` (отсутствующий токен) или из `container.setup()` (например, неверный `LOGGER_DEFAULT`) всплывает в `bootstrap()` и попадает в `bootstrap().catch(fail)`; исключение внутри `Bot.run()` сначала логируется как `critical`, затем пробрасывается туда же. Ошибка печатается через `console.error`, а не структурированным `Logger`: на момент сбоя логгер может быть ещё не собран. Дополнительно `app.ts` регистрирует `process.on("unhandledRejection", fail)` и `process.on("uncaughtException", fail)`, поэтому асинхронный сбой уже после старта тоже завершает процесс с кодом 1, а не остаётся незамеченным.

**Побочные эффекты:** один вызов Telegram API (`setMyCommands`) при каждом старте процесса, независимо от того, изменились ли команды.

## 2. Остановка процесса

**Триггер:** `SIGINT` или `SIGTERM` (например, `Ctrl+C`, `docker stop`, сигнал остановки от менеджера процессов). Оба подключены через `process.once(...)` в `app.ts`, так что **обрабатывается только первый полученный сигнал** — второй `SIGINT` во время остановки не делает ничего дополнительного (запасного принудительного выхода нет).

**Последовательность:**
1. `gracefulStop()` (`app.ts`) → `stop()` → `bot.stop()` → `container.close()`; после успешного `stop()` — `process.exit(0)`.
2. `Bot.stop()`:
   - Логирует `"Stop bot..."`.
   - Если `!this.isRun`, логирует `"Bot is not running!"` и сразу выходит (ничего не делает).
   - Если runner работает, `await this.runner.stop()` — останавливает long-polling; новые апдейты от Telegram после этого не забираются, но уже находящиеся в пайплайне middleware апдейты доигрывают до конца (семантика runner'а grammY; в коде этого репозитория не проверялась, но стандартна для `@grammyjs/runner`).
   - `await this.waitPlannerToEmpty()` — опрашивает `planner.isEmpty()` каждые 3000 мс в **неограниченном цикле `while (true)` без таймаута и без максимума итераций**. `isEmpty()` проверяет только, что три приоритетные корзины не содержат *поставленных в очередь* сообщений, — он **не** проверяет, завершился ли текущий выполняющийся вызов `handleMessage()` в `Broker`. Если очередь не пуста из-за бага повторной постановки при ошибке, описанного в Потоке 4 (сообщение, которое всё падает и бесконечно возвращается в приоритет `HIGH`), **этот цикл никогда не завершится**, и остановка процесса зависнет навсегда: обработка `SIGTERM`/`SIGINT` не доходит до конца, и (в зависимости от супервизора процессов на хосте) процесс может потребовать принудительного убийства (`SIGKILL`).
   - `await this.broker.stop()` — выставляет `Broker._isRun = false`. Поскольку рекурсивный цикл `Broker.handleMessages()` проверяет `this.isRun` в начале каждой итерации (см. Поток 4), цикл выйдет на следующей итерации, а не немедленно; но так как `stop()` не дожидается фактического завершения этого цикла, между «planner сообщил, что пуст» и «цикл broker'а действительно перестал рекурсировать» остаётся небольшая незакрытая гонка.
   - `this.isRun = false`, лог `"Bot is successfully stopped."`.
3. `container.close()` — `Container.close()` является заглушкой: `if (!this.alreadySetup) return;`, а в остальном **не делает вообще ничего** — ни сброса `alreadySetup = false`, ни вызова `database.sql.end()`. Пул соединений Postgres из шага 2 Потока 1 **никогда явно не закрывается**; процесс целиком полагается на выход из процесса, чтобы разорвать TCP-соединения (это работает, но означает, что аккуратный `SIGTERM` на самом деле не сливает и не закрывает пул БД корректно — например, запросы, выполняющиеся в момент выхода, просто бросаются, а не доигрывают и не отменяются явно).

**Изменения состояния:** `Bot.isRun = false`; `Broker._isRun = false` (в итоге); состояние DI-контейнера в остальном не тронуто (`alreadySetup` навсегда остаётся `true`, то есть `container.setup()` был бы пустой операцией, если бы его вызвали снова в том же процессе — для текущей кодовой базы неактуально, поскольку дважды его никто не вызывает, но актуально, если процесс когда-нибудь научат перезапускать бота на месте).

**Обращения к хранилищу:** явных нет (пул бросается, а не сливается).

**Внешние вызовы:** нет, кроме тех, что вызовет ещё доигрывающая обработка апдейтов (если она есть).

**Обработка ошибок:** сами шаги `stop()` в try/catch не обёрнуты, но вызов целиком обёрнут в `gracefulStop()`: исключение в любом месте цепочки (например, реджект `runner.stop()`) печатается через `console.error`, и процесс завершается с кодом 1 вместо кода 0. Необработанного reject промиса из обработчика сигнала больше не возникает.

**Побочные эффекты:** никаких, кроме логов, — если только неограниченный цикл `waitPlannerToEmpty()` не зависнет навсегда; в этом случае практический побочный эффект — «процесс придётся убивать принудительно».

## 3. Входящий апдейт Telegram → пайплайн middleware

**Триггер:** цикл long-polling из `@grammyjs/runner` получает апдейт от Telegram (`getUpdates`) и передаёт его в `Bot.handleUpdate(update, ...)` grammY.

**Важная деталь фреймворка (проверено по исходникам grammY `v1.10.1`, `src/bot.ts`):** для каждого апдейта grammY создаёт **новый экземпляр `Api`** — `const api = new Api(this.token, this.clientConfig, webhookReplyEnvelope)`, — копирует в него установленные трансформеры из `bot.api` и передаёт этот свежий экземпляр в конструктор `Context`. **Поэтому `ctx.api` никогда не является тем же объектом, что `bot.api`, и никакие два апдейта не делят экземпляр `Api`.** Это напрямую важно для Потока 4.

**Последовательность (пайплайн middleware, в точном порядке регистрации из `Bot.setup()`):**

1. **Session middleware** (`session({ initial: initialPayload, getSessionKey, storage: PgsqlStorage })`, ядро grammY, подключается в `setupSession()`).
   - `getSessionKey(ctx)` (`session.helper.ts`) возвращает `` `${ctx.from.id}:${ctx.chat.id}` `` либо **`undefined`**, если отсутствует `ctx.from` или `ctx.chat`.
   - **Ветка A (ключ разрешён):** session-middleware grammY лениво загружает строку по этому ключу через `PgsqlStorage.read(key)` (`SELECT * FROM sessions WHERE key = ...`) при первом обращении к `ctx.session` в рамках этого апдейта — или использует `initialPayload()` (`{ requestCount: 0 }`), если строки ещё нет. Вызывается `next()`; после завершения нижележащей цепочки, если данные сессии читались/трогались и «загрязнены», grammY записывает их обратно через `PgsqlStorage.write(key, value)` (upsert в `sessions`, точный запрос — в architecture.md §11; отметим, что там используется позиционный `VALUES (key, value)` без явного списка колонок, с опорой на `DEFAULT now()` у `created_time`/`updated_time` в миграции; это реальная, но сейчас безобидная связанность с порядком колонок).
   - **Ветка B (ключ не разрешён, отсутствует `ctx.from` или `ctx.chat` — например, пост в канале):** grammY всё равно немедленно вызывает `next()` (проверено по исходникам `v1.10.1`), так что пайплайн продолжается, — но определение свойства `session` на `ctx` устроено так, что **первое же обращение к `ctx.session` синхронно бросает исключение** (`"Cannot access lazy session data because ... returned undefined for this update!"`). Чтения/записи сессии в этой ветке не происходит (читать и писать нечего).

2. **`sequentialize()`** (`@grammyjs/runner`, подключается в `setupSequential()`) — вычисляет массив ключей из `[ctx.chat?.id, ctx.from?.id]` (что присутствует) и обеспечивает, чтобы апдейты, разделяющие любой из этих ключей, обрабатывались по одному относительно друг друга, хотя runner забирает и раздаёт апдейты конкурентно. Существует именно для того, чтобы два апдейта от одного пользователя/чата не устроили гонку на чтении/записи `ctx.session`.

3. **`TelegramCallApiMiddleware`** — подробности в Потоке 4. Синхронно подменяет `ctx.api.raw` (свежий экземпляр на апдейт, см. замечание о фреймворке выше) на `Proxy`, затем вызывает `next()`. Собственной ветки ошибок нет — сам `handle()` в нормальных условиях бросить исключение не может.

4. **`AsyncLocalStorageMiddleware`** — разрешает `Infrastructure.Logger` из контейнера. Если это **не** экземпляр `PinoLogger` (то есть активен `ConsoleLogger` — дефолт для разработки), он просто вызывает `next()` и больше ничего не делает: **корреляции запросов в этом режиме нет.** Если это **действительно** `PinoLogger`, он создаёт `logger.child({ requestId: uuid() })` и выполняет остаток пайплайна внутри `asyncLocalStorage.run(new Map([["logger", child]]), next)` — с этого момента и до конца обработки данного апдейта (а также во всём, что достижимо из него по асинхронному продолжению) любой код, разрешающий `Infrastructure.Logger` через Proxy-биндинг `PinoLogger` в контейнере, получает этот дочерний логгер запроса вместо общего синглтона (см. `docs/architecture.md` §4/§9).

5. **`ResponseTimeMiddleware`** — фиксирует `Date.now()`, делает `await next()`, затем логирует `` `Response time: ${end - start} ms` `` на уровне `info`. **Без try/catch** — если `next()` реджектится (как в Ветке B ниже), вызов этого middleware реджектится тоже, и строка лога со временем не выполняется никогда.

6. **`RequestLogMiddleware`** — `context.session.requestCount++` является **первой инструкцией**, за ней следует `this.logger.debug("Request", context.update)` (логирует **весь сырой объект апдейта Telegram** — включая текст сообщения и любые идентифицирующие пользователя поля из `ctx.update.message.from`, на уровне `debug`; это стоит держать в голове как вопрос утечки данных, если debug-логи когда-нибудь начнут уезжать куда-то менее доверенное, чем локальный диск).
   - **Ветка A (ключ сессии разрешён на шаге 1):** инкрементирует и (в итоге, через обратную запись сессии на шаге 1) сохраняет счётчик запросов на пару пользователь+чат. Это *единственное* место во всей кодовой базе, где `SessionPayload.requestCount` читается или пишется, — он считается, но нигде не отображается и ни на что не влияет.
   - **Ветка B (ключ сессии был `undefined`):** `context.session` синхронно бросает исключение в момент обращения. **Это подтверждённая находка рантайм-бага:** исключение всплывает через незащищённый `await next()` в `ResponseTimeMiddleware`, через `next` в `AsyncLocalStorageMiddleware` (независимо от того, прошёл ли путь через обёртку `asyncLocalStorage.run()` — исключение внутри колбэка нормально всплывает из `.run()`), через `sequentialize()` и внутренний try самого session-middleware (session-middleware grammY не проглатывает ошибки нижележащих слоёв — см. комментарий `// no catch: do not write back if middleware throws` в его исходниках: он намеренно пробрасывает исключение дальше) — и в конце концов выходит из вызова `run(this.middleware(), ctx)` внутри `handleUpdate` в grammY, который переупаковывает его в `BotError` и передаёт тому, кто зарегистрирован через `bot.catch(...)`, то есть `Bot.handleError`, который логирует `critical("Unhandled error on bot", error)`. **Обработка этого апдейта на этом заканчивается.** `FillUserToContextMiddleware`, flavor i18n, фильтр приватного чата и вся диспетчеризация команд/conversation'ов для такого апдейта **не выполняются вообще**.
   - **Следствие:** собственная явная защита `if (!ctx.from) { this.logger.error(...); return; }` в `FillUserToContextMiddleware` **на практике недостижима**: к моменту, когда управление могло бы до неё дойти, пайплайн уже упал на `RequestLogMiddleware` — ровно для того же класса апдейтов (любой апдейт без `ctx.from`, поскольку `getSessionKey` его требует). Эта защита — мёртвый код; исходное описание в `docs/architecture.md` как «механизма, которым такие апдейты молча отбрасываются» исправлено: настоящий механизм отбрасывания — это более раннее необработанное исключение, а не явная проверка.

7. **`FillUserToContextMiddleware`** (достигается только при наличии `ctx.from`, см. выше, — то есть у его собственной ветки `if (!ctx.from)` живого пути в нормальной работе нет):
   - `await this.userRepository.existsById(ctx.from.id)` — `SELECT id FROM users WHERE id = ...`.
   - **Ветка A (существует):** `userService.edit(ctx.from.id, {...})` → `UserService.edit` делает `repository.getById(id)` (ещё один `SELECT * FROM users WHERE id = ... LIMIT 1`, то есть **два отдельных `SELECT` к `users` на апдейт** для вернувшегося пользователя, плюс последующий `save()` — итого три обращения), применяет поля частичного DTO через сеттеры загруженной сущности `User` (каждый сеттер автоматически проставляет `updatedTime`), затем `repository.save(user)` (`INSERT ... ON CONFLICT (id) DO UPDATE ...`).
   - **Ветка B (не существует):** `userService.create({...})` → создаёт новый `User` с `lastActiveTime = createdTime = updatedTime = dayjs()` (все равны «сейчас»), затем `repository.save(user)` (тот же запрос upsert — именно на него полагаются как на фактический механизм предотвращения дублей, поскольку сам `create()` проверки существования не делает).
   - Обе ветки выставляют `ctx.user` в получившуюся сущность `User` — **это единственное место, где `ctx.user` заполняется**; любой нижележащий код команд/conversation'ов, читающий `ctx.user`, зависит от того, что этот middleware отработал без исключений.
   - В конце обеих веток вызывается `next()`.
   - **Обработка ошибок:** отсутствует — если `existsById`, `edit` или `create` бросит исключение (например, ошибку БД или `UserCreateError`/`UserEditError`, обёрнутый вокруг сбоя БД), оно без защиты всплывёт до `Bot.handleError`, тем же терминальным путём, что и в Ветке B выше (обработка апдейта прекращается, ничего нижележащего не выполняется, пишется critical-лог).

8. **Flavor i18n Fluent** (`useFluent(...)`) — цепляет `ctx.t(key, params)`, привязанный к тому, что вернёт `localeNegotiator`, а он **захардкожен и всегда возвращает `"ru"`** независимо от реальной локали апдейта/пользователя. Никаких условий, никакого чтения состояния.

9. **`IsPrivateChatFilter`** — `ctx.chat?.type === "private"`. Если **false** (группа, супергруппа, канал), `composer.filter()` grammY просто **обрывает цепочку здесь** — это не ошибка, никаких исключений, обычное поведение отфильтрованного middleware; ничего нижележащего (conversations, команды) для не-приватных чатов не выполняется. Именно этот механизм на практике делает весь бот работающим только в приватных чатах, несмотря на настроенные в `Planner` групповые рейт-лимиты (см. architecture.md §6), намекающие, что поддержка групп задумывалась/была частично реализована.

10. **Conversations** (`conversations()` + по одному `createConversation(...)` на зарегистрированный обработчик) — плагин conversation'ов grammY перехватывает апдейты для чатов, находящихся «внутри» conversation (состояние отслеживается через сессию, ту же самую на `PgsqlStorage`, что и на шаге 1), и направляет их в соответствующий `ConversationHandler.handle()` вместо обычного сопоставления команд. См. Поток 5.

11. **Команды** (`composer.command(name, handler)` на каждую зарегистрированную `Command`) — grammY сопоставляет текст `/command` с зарегистрированными именами команд и вызывает `Command.handle(ctx)`. По каждой конкретной команде — Потоки 5–7.

**Изменения состояния (сводно для «счастливого пути» апдейта):** строка `sessions` прочитана и (если загрязнена) записана upsert'ом; строка `users` прочитана (1–2 раза) и записана upsert'ом; `ctx.user`/`ctx.session` заполнены на время обработки этого апдейта (после — отбрасываются, нигде дольше не хранятся).

**Обращения к хранилищу (сводно):** до 1 `SELECT` + 1 upsert по `sessions`; до 2 `SELECT` + 1 upsert по `users` на каждый апдейт, дошедший до `FillUserToContextMiddleware`.

**Внешние вызовы:** в самом пайплайне отсутствуют (исходящие вызовы Telegram порождает то, что делает обработчик команды/conversation — см. Поток 4).

**Обработка ошибок (сводно):** есть ровно один перехватчик верхнего уровня (`Bot.handleError`, зарегистрированный через `grammy.catch(...)`), и он не делает ничего, кроме логирования на уровне `critical`, — ни повторов, ни какого-либо сообщения об ошибке пользователю Telegram, чей апдейт вызвал сбой, никогда не отправляется. С точки зрения пользователя упавший апдейт просто не порождает ответа бота, без каких-либо признаков, что что-то пошло не так.

**Побочные эффекты:** записи в БД, как описано выше; строки логов на уровне `debug` (сырой payload апдейта, если сработала ветка A в `RequestLogMiddleware`), `info` (время ответа) и, возможно, `critical` (любая необработанная ошибка).

## 4. Исходящий вызов Telegram API (пайплайн ограничения скорости)

**Триггер:** любой код, вызывающий метод на `ctx.api` (напрямую или косвенно через удобные методы вроде `ctx.reply(...)`, которые под капотом зовут `ctx.api.sendMessage(...)`) во время обработки какого-либо апдейта.

**Область действия — важное исправление к документу первого прохода:** механизм перехвата устанавливается в `TelegramCallApiMiddleware.handle()`, который выполняется один раз на апдейт и мутирует **собственный, только что созданный `ctx.api` этого апдейта** (см. замечание о фреймворке в Потоке 3 — каждый апдейт получает от grammY свой экземпляр `Api`, никогда не разделяемый ни с `bot.grammy.api`, ни с другими апдейтами). Отсюда два следствия, ни одно из которых не очевидно при чтении `telegram-call-api.middleware.ts` в отрыве:
- **Накопления обёрток `Proxy` между апдейтами не происходит** — каждый апдейт независимо оборачивает свой нетронутый `.raw`, и обёрнутый экземпляр отбрасывается по завершении обработки апдейта. (Возникшая по ходу анализа гипотеза, что повторное оборачивание на каждом апдейте могло бы наслаивать `Proxy` на общий объект `Api`, была проверена по реальным исходникам grammY и опровергнута: `handleUpdate` каждый раз создаёт `new Api(...)`. Отмечено здесь, чтобы опровергнутая идея не была случайно «переоткрыта» позже.)
- Код, который вместо этого вызывает напрямую **`bot.grammy.api`** (синглтон `Api` уровня бота, создаваемый один раз в конструкторе `Bot`), **полностью минует этот перехват** — `.raw` того экземпляра `TelegramCallApiMiddleware` никогда не трогает. `BulkMessagesCommand` и мёртвый метод `StartCommand.sendRandomText` делают ровно это, и оба компенсируют это ручным вызовом `planner.push(...)` вместо опоры на автоматический перехват — то есть два механизма (автоматический через `ctx.api` и ручной через прямой `planner.push`) сосуществуют по необходимости, а не благодаря общему коду.

**Последовательность для вызова через `ctx.api` (типичный случай, например `ctx.reply(text)`):**

1. Слой `Api` в grammY собирает payload в виде простого JS-объекта (например, `{ chat_id, text }`) и вызывает `ctx.api.raw[method](payload, signal)`. Поскольку `ctx.api.raw` был заменён на `Proxy` на шаге 3 Потока 3, срабатывает ловушка `get` прокси, возвращающая `callApi.bind(api, method)`.
2. Выполняется `callApi(method, payload, signal)`:
   - **Ветка — вызов не отслеживается:** `payload.constructor.name !== "Object"` (например, payload в духе `FormData` для методов, напрямую загружающих файл, или любой payload, не являющийся простым объектом) **или** `!("chat_id" in payload)` → вызывается `originRaw[method](payload, signal)` напрямую, полностью минуя очередь. **Это означает, что любой вызов Telegram API, загружающий файл как multipart form data, этим механизмом не ограничивается по скорости вовсе** — ограничиваются только вызовы с простым объектом (как правило, JSON-payload). Ни `/font_generator`, ни отладочный код `/start` файл фактически не загружают (см. находку №1 в Потоках 6/7), так что в текущей кодовой базе эта ветка ни одним живым путём не задействуется, но это реальный пробел в покрытии перехвата.
   - **Ветка — исключение для групп:** `chatId = Number(payload.chat_id)`; `isGroup = chatId < 0` (отрицательные ID — соглашение Telegram для групп/супергрупп); если `isGroup && TELEGRAM_NO_GROUP_RATE_LIMIT_SET.has(method)` (белый список из 5 методов: `getChat`, `getChatAdministrators`, `getChatMembersCount`, `getChatMember`, `sendChatAction`) — вызывается `originRaw[method](payload, signal)` напрямую. **Обратите внимание: этот белый список применяется только к групповым чатам** — для приватных чатов ни один из этих методов (как и любой другой) очередь не пропускает: каждый приватный вызов с простым объектом и `chat_id` идёт через очередь, даже дешёвые read-only вроде `getChat`.
   - **Ветка — `isNaN(chatId)`:** тоже напрямую минует очередь (защитная обработка некорректных/отсутствующих chat ID).
   - **Ветка по умолчанию — в очередь:** создаётся `Promise` (с сохранением его `resolve`/`reject` в `messageResolve`/`messageReject`), строится замыкание `callback` (см. шаг 3) и вызывается `planner.push({ chatId, isGroup, priorityOnError: PRIORITY.HIGH, callback }, PRIORITY.MEDIUM)` — **все вызовы, попадающие в очередь этим путём, кладутся с приоритетом `MEDIUM`**; путь автоматического перехвата никогда не порождает сообщений с приоритетом `HIGH` или `LOW` (те появляются только через ручные вызовы `planner.push()` в `BulkMessagesCommand`/мёртвом коде `StartCommand` и через `priorityOnError` при повторе — см. ниже). Вызывающей стороне возвращается `Promise` (то есть обратно через слой `Api` grammY тому, кто ждал `ctx.reply(...)`).
3. **`Planner.push`** добавляет объект сообщения в массив `MEDIUM`. При добавлении слоты не проверяются — только при извлечении.
4. Независимо от этого самовызывающийся цикл `Broker`'а (запущен в Потоке 1 и крутящийся непрерывно всё время жизни процесса, пока `_isRun` истинно) на каждой итерации вызывает `Planner.pull()`:
   - Немедленно возвращает `null`, если действует глобальный бан, если все три очереди пусты или если общий `SlotManager` (`commonManager`) не свободен (`common`: по умолчанию 30/1000 мс, или что там разрешат `LIMIT_COMMON_*`).
   - Иначе сканирует `HIGH` → `MEDIUM` → `LOW`; внутри каждой корзины идёт с начала к концу в поисках первого сообщения, у которого свободен *его чатовый* `SlotManager` (создаётся лениво на каждый `chatId`, с лимитами `group`/`private` — дефолты `.env.dist`: 3/1000 мс для приватных, 20/60000 мс для групп). Если найдено: **резервирует и общий слот, и слот чата**, вырезает сообщение из его корзины (чтобы оно не нашлось повторно) и возвращает его.
   - Если подходящего сообщения нет ни в одной корзине (например, все стоящие в очереди сообщения зажаты рейт-лимитом своих чатов), возвращает `null`, хотя очереди и не пусты.
5. **Когда `pull()` возвращает сообщение,** выполняется `Broker.handleMessage(message)`: `try { await message.callback(); } catch (error) { this.handleError(error); this.planner.push(message, message.priorityOnError); }`.
6. **`message.callback()` — это замыкание, построенное на шаге 2:** `async () => { try { messageResolve(originRaw[method](payload, signal)); } catch (e) { messageReject(e); } }`.

**Именно здесь и живёт подтверждённый рантайм-баг.** `originRaw[method](payload, signal)` — это настоящий, не проксированный низкоуровневый вызов API grammY: `async`-метод, который выполняет реальный HTTP-запрос к Telegram и **возвращает Promise**; в нормальных сценариях отказа он не бросает исключение синхронно (сетевые ошибки, HTTP 4xx/429/5xx и прочее приходят как *reject* этого возвращённого Promise, а не как синхронные исключения — это стандартное поведение HTTP-клиента на основе `async function`, и гадать здесь не пришлось: любая объявленная `async` функция в JS не может бросить исключение синхронно вызывающему коду, `throw` внутри неё становится reject'ом Promise). Замыкание `callback` **не делает `await`** над этим внутренним вызовом — оно просто передаёт ещё не завершённый Promise прямо в `messageResolve(...)`. По семантике Promise, резолв Promise'а другим Promise'ом (thenable) заставляет внешний Promise «перенять» итоговое состояние внутреннего, — поэтому **Promise исходной вызывающей стороны** (тот, который на самом деле ждёт `ctx.reply(...)` и т. п.) *действительно* в итоге окажется отклонённым, если реальный вызов Telegram упадёт, как только тот завершится.

Но **сам** `callback()`, будучи `async function`, в теле которой нет ни одного `await`, завершается синхронно (ошибок нет, `messageResolve` не падает от того, что ему передали Promise), и его собственный возвращённый Promise резолвится в `undefined` на следующем микротике — **независимо от того, успешно ли позже завершится настоящий вызов Telegram.** Как следствие:

- `await message.callback()` в `Broker.handleMessage` практически в любых реальных условиях завершится без исключения.
- Его блок `catch` — единственное место, где вызываются `handleError` (который распознаёт HTTP 429 и зовёт `planner.ban(retry_after * 1000)`) и повторная постановка при сбое (`planner.push(message, message.priorityOnError)`), — поэтому **на практике почти наверняка не выполняется никогда**. Он сработал бы только если бы сам `originRaw[method]` бросил исключение *синхронно*, что означало бы баг в низкоуровневом API-клиенте grammY, а не обычный сбой на стороне Telegram.
- **Практическое следствие:** когда Telegram отвечает `429 Too Many Requests`, вызывающая сторона `ctx.reply(...)` (или что там инициировало вызов) *в итоге* увидит reject (через описанное выше перенимание состояния промиса) — но ничто в `Broker`/`Planner` на это не реагирует. `Planner.ban()` не вызывается, поэтому бот продолжает отправлять с настроенной частотой слотов, как ни в чём не бывало, полагаясь исключительно на то, что Telegram будет отклонять последующие вызовы, а не отступая проактивно. Точно так же упавшее сообщение **не** ставится в очередь повторно — с точки зрения Broker'а оно просто теряется (исходная вызывающая сторона сбой видит, но автоматического повтора нет).
- Код, изначально вызвавший `ctx.reply(...)` (или подобное), скорее всего не обёрнут в собственный `try/catch` в этой кодовой базе (ни один из рассмотренных обработчиков команд не перехватывает ошибки своих же вызовов `ctx.reply` на верхнем уровне — см. Потоки 5–7), поэтому итоговый reject всплывает так же, как любая другая ошибка пайплайна: как необработанный reject, который (в зависимости от того, где именно в асинхронной цепочке это происходит относительно собственных границ обработки ошибок grammY) скорее всего окажется залогирован через `Bot.handleError` как `critical` «Unhandled error on bot» — без автоматического повтора и без какого-либо реального отступления по рейт-лимиту, хотя структурно код выглядит реализующим и то, и другое.
- Эта находка выведена статической трассировкой точной механики Promise (проверено дважды), а не запуском кода; она названа **подтверждённой**, а не догадкой, потому что не зависит ни от какого внешнего непроверяемого допущения — только от того, как ведут себя `async`/`await`/`Promise.resolve(thenable)`, а это специфицированное поведение JS.

**Замечание по конфигурации:** интервал опроса `Broker`'а при простое (используется только когда `Planner.pull()` вернул `null`, то есть очередь пуста или сейчас ничего не подходит) по умолчанию в коде равен **1000 мс** (`Config.getEnvAsInteger("BROKER_SLEEP_INTERVAL", 1000)`), но закоммиченный `.env.dist` переопределяет его на **`10`** (мс) — куда более агрессивная частота холостого опроса, чем можно предположить, читая только `config.ts` в отрыве.

**Когда подходящее сообщение *есть*, цикл Broker'а не дожидается его завершения**, прежде чем проверить следующее: рекурсивная ветка `handleMessages()` (`await this.handleMessage(message); return this.handleMessages();`) из-за описанного выше бага резолвится практически мгновенно, независимо от того, сколько длится настоящий HTTP-вызов к Telegram. То есть реальная пропускная способность цикла ограничивается исключительно резервациями `SlotManager`, а не сетевой задержкой, — свойство разумное (пусть и случайное), но это прямое следствие того же бага в работе с Promise, а не намеренный дизайн «отправил и забыл», задокументированный где-либо в коде.

**Изменения состояния:** `SlotManager.reserveTimeout` выставляется (и общий, и на чат) при каждом успешном `pull()`; `Planner.managers` получает новую запись при первом появлении любого `chatId` (и никогда не теряет её — см. issue [#32](https://github.com/yuldashevsardor/telegram-bot/issues/32)).

**Обращения к хранилищу:** в самом этом потоке отсутствуют (всё в памяти).

**Внешние вызовы:** собственно HTTP-вызов Telegram Bot API, выполняемый изнутри замыкания `callback` через `originRaw[method](payload, signal)`.

**Обработка ошибок:** как описано выше — структурно присутствует (`try/catch` + повторная постановка + бан по 429), но практически недостижима для доминирующего режима отказа (асинхронный reject реального HTTP-вызова). *Единственные* ошибки, которые дошли бы до блока catch в `Broker.handleMessage`, — синхронные исключения при самом вызове `originRaw[method]`.

**Побочные эффекты:** ровно один реальный исходящий вызов Telegram API на каждое извлечённое сообщение (когда не сработали ветки обхода очереди); `console.log("broker error", error)`, если (редко достижимый) блок catch всё же сработает; `console.log(`Ban expires in ...`)` каждые 10 секунд, пока активен бан (из `Planner.logBanExpires`, который сам по себе на практике мёртв, поскольку `Planner.ban()`, согласно вышесказанному, вызывается редко или никогда).

## 5. Команда `/start` → `StartConversation`

**Триггер:** апдейт из приватного чата с текстом `/start` (сопоставляется `composer.command("start", ...)` в grammY, достигается только после прохождения всего пайплайна из Потока 3, включая фильтр приватного чата).

**Последовательность:**
1. `StartCommand.handle(ctx)` — *единственная* живая строка в этом обработчике: `return this.startConversation.enter(ctx)`.
2. `ConversationHandler.enter(ctx)` → `ctx.conversation.enter("start")` — плагин conversations grammY помечает этот чат как находящийся «внутри» conversation `"start"` (сохраняется через сессию, тот же бэкенд `PgsqlStorage`, что и в шаге 1 Потока 3) и немедленно начинает выполнять `StartConversation.run()` (функция, зарегистрированная через `createConversation(handler.handle.bind(handler), "start")` в `Bot.setupConversations()`).
3. `StartConversation.run()`:
   - `const text = this.ctx.t("welcome", { formats: "woff, woff2, otf, ttf" })` — разрешает ключ `welcome` из единственного русского файла `.ftl` через Fluent (локаль всегда `"ru"`, см. шаг 8 Потока 3 / Поток 8).
   - `await this.ctx.reply(text)` — исходящий вызов, идёт по пайплайну Потока 4 (в очередь, приоритет `MEDIUM`, под ограничением приватного `SlotManager`).
   - `const nextMessage = await this.conversation.wait()` — плагин conversations grammY **приостанавливает выполнение здесь** и возвращает управление фреймворку; *следующий* апдейт из этого же чата (любого вида — любое сообщение) будет направлен обратно ровно в эту точку `run()` вместо обычной диспетчеризации команд, и выполнение продолжится с `nextMessage`, привязанным к контексту того апдейта. Именно так пайплайн «ставится на паузу» посреди conversation; состояние о том, где каждый стек conversation приостановлен, хранится в сессии.
   - `await nextMessage.reply(nextMessage.message?.text || "Чет не получилось...")` — отправляет обратно тот текст, что только что прислал пользователь, либо **захардкоженную русскую запасную строку**, если во входящем апдейте нет `message.text` (например, стикер, фото или другое нетекстовое сообщение). Этот запасной вариант полностью минует Fluent (`ctx.t(...)`), то есть не уважает тот же механизм i18n, который номинально использует остальная часть conversation, — хотя сегодня этот механизм всё равно всегда разрешается в русский.
   - Затем `run()` завершается, закрывая conversation для этого чата.

**Условия/ветвления:** единственная настоящая ветка — «содержал ли возобновивший апдейт текст», она обрабатывается вышеописанным `||`.

**Изменения состояния:** флаг активной conversation и точка возобновления сохраняются в сессии (через собственное использование сессии плагином conversations) в промежутке между `reply` и возобновлением `wait()`; очищаются, как только `run()` завершается.

**Обращения к хранилищу:** те же чтения/записи сессии, что и для любого апдейта (шаг 1 Потока 3), но для *двух* отдельных апдейтов (сама команда `/start` и последующее сообщение, возобновляющее `wait()`); плюс upsert в `users` из `FillUserToContextMiddleware`, который отрабатывает независимо для обоих этих апдейтов (это обычный middleware пайплайна, ничего не знающий про conversations).

**Внешние вызовы:** два исходящих сообщения (`ctx.reply(welcomeText)` и `nextMessage.reply(...)`), оба идут через Поток 4.

**Обработка ошибок:** внутри `run()` отсутствует — любой сбой (например, итоговый reject `ctx.reply` по багу из Потока 4) всплывает без защиты тем же терминальным путём, что и любая другая ошибка пайплайна (раздел «Обработка ошибок» в Потоке 3).

**Побочные эффекты:** два сообщения Telegram, отправленных пользователю (с учётом очереди из Потока 4); отметим, что `StartCommand` также определяет два приватных метода, `generateRandomFonts` и `sendRandomText`, которые **никогда не вызываются из `handle()`**, — мёртвый код, оставшийся от разработки/тестирования и не входящий ни в один живой поток. (`sendRandomText` — уменьшенный близнец паттерна `BulkMessagesCommand`, см. Поток 7: он вручную кладёт сообщения в `Planner`, обращаясь напрямую к `bot.grammy.api`, а не к `ctx.api`.)

## 6. Команда `/font_generator` (пайплайн конвертации шрифтов)

**Триггер:** апдейт из приватного чата с текстом `/font_generator`.

**Последовательность:**
1. `FontGeneratorCommand.handle(ctx)`:
   ```ts
   const promises: Promise<unknown>[] = [];
   for (let i = 0; i < 1; i++) {
       promises.push(this.generateRandomFonts.bind(this, ctx));
   }
   await Promise.all(promises);
   ```
   **Подтверждённый баг (структурно выявлен ещё первым проходом, здесь переподтверждён с точным рантайм-следствием):** `this.generateRandomFonts.bind(this, ctx)` даёт **ссылку на привязанную функцию**, а не вызов — `generateRandomFonts` не вызывается никогда. В `promises` оказывается одно значение-функция, не являющееся Promise; `Promise.all([fn])` резолвится немедленно (не-thenable значение в массиве трактуется как уже разрешённое). **Обработчик команды не делает вообще ничего наблюдаемого** — ни ответа, ни конвертации шрифта, ни ошибки: пользователь отправляет `/font_generator`, и бот молча ничего не делает. Об этом стоит сказать явно, поскольку исходный документ по архитектуре описывал задуманный пайплайн (это реальный, корректно написанный код), не проговаривая до конца, что в текущей сборке **он никогда не выполняется**.
2. **Что `generateRandomFonts(ctx)` *делал бы*, если бы его действительно вызывали** (сегодня мёртвый код, но проследить стоит: это единственное место, где доменная логика font-convertor из `docs/architecture.md` §7 вообще задействуется, и тот же паттерн продублирован — и *является живым* — в `StartCommand.generateRandomFonts`, достижимом только через столь же мёртвый приватный метод той команды):
   - Для каждого из `EOT`, `OTF`, `TTF`, `WOFF2` (четыре целевых расширения, захардкожены, конвертация всегда из одного фиксированного исходного файла `tempDir/app/test-fonts/test-font.woff`):
     - `FontConvertor.convert({ originPath: woffPath, extension })`:
       - `prepare()` (идемпотентно, флаг `isPrepared`) проверяет, что `tempDir` существует, читаем, доступен для записи и является директорией, иначе бросает типизированные ошибки (`InvalidPath`/`PermissionDenied`).
       - Выводит исходное расширение из пути; бросает `FontConvertorError`, если оно совпадает с целевым (здесь невозможно, так как источник всегда `.woff`, а целевые никогда не `woff`).
       - Генерирует случайное имя файла из 15 символов + целевое расширение.
       - **`FileHelper.createDirectoriesByDate(tempDir)`** — создаёт `tempDir/<год>/<месяц 1-12>/<день месяца 1-31>`, то есть календарную структуру `YYYY/M/D`. До issue [#30](https://github.com/yuldashevsardor/telegram-bot/issues/30) самый глубокий сегмент брался из `dayjs().day()` — это **день недели** (`0`–`6`, воскресенье = `0`), а не день месяца, — поэтому раскладка принимала всего 7 значений и **циклилась еженедельно**: файлы, сгенерированные в две разные среды с разницей в четыре недели, попадали в одну и ту же директорию `<год>/<месяц>/3`. Оставшиеся от старой схемы каталоги `0`–`6` из `TEMP_DIR` не вычищались — это учитывать задаче об очистке временных файлов (issue [#37](https://github.com/yuldashevsardor/telegram-bot/issues/37)).
       - `ConvertorFactory.get(from, to)` направляет вызов в один из примерно 20 конкретных классов пар; бросает `ConvertorNotFound` для любой неподдерживаемой пары (в частности, для всего, что связано с `SVG`, для которого зарегистрированных пар нет, хотя он и присутствует в `FontForge.supportedExtensions`).
       - `validate()` конкретного конвертора проверяет, что исходный файл существует, читаем, является файлом и имеет ожидаемое расширение, а также что выведенный из расширения MIME-тип (через пакет `mime-types`) входит в список `allowedMimeTypes` конвертора; затем тот же набор проверок для пути назначения (он **не** должен существовать, родительская директория должна быть читаемой, доступной для записи и быть директорией, расширение — корректным).
       - `FontForge.convert(src, dist)` собирает shell-команду наивным `.replace()` по строке (без экранирования) и запускает её через `child_process.exec` (промисифицированный). При сбое оборачивает ошибку через `ExecuteError.byError(error)`.
     - **`await ctx.reply(eotPath)`** (и аналогично для путей otf/ttf/woff2). **Подтверждённая находка:** здесь отправляется **строка локального пути в файловой системе сервера** (например, `/app/tmp/2026/8/1/kx8n2q1p3z7m9wq.eot`) как обычный *текст* сообщения — сам сконвертированный файл шрифта **не** загружается и не прикрепляется. Реальный конечный пользователь получает четыре текстовых сообщения с путями на файловой системе самого бота, а не пригодные к использованию файлы шрифтов. Первый проход в `docs/architecture.md` описывал этот поток как «сконвертированный файл отправляется обратно пользователю» — эта более глубокая трассировка исправляет описание: сам файл не передаётся никогда, только его путь.
   - Всё обёрнуто в `try/catch`, который делает лишь `console.log(error)`, полностью минуя структурированный `Logger` (сырой `console.log`, тот же паттерн, что отмечен для `Broker.handleError`/`Planner.logBanExpires` в `docs/architecture.md` §6).

**Условия/ветвления:** ничего, кроме фиксированного цикла по 4 расширениям; пользовательский ввод не читается вообще (исходный файл шрифта и все четыре целевых расширения захардкожены).

**Изменения состояния:** временные файлы, создаваемые на диске в `tempDir/<год>/<месяц>/<день месяца 1-31>/`; в базах данных — ничего.

**Обращения к хранилищу:** отсутствуют (конвертация шрифтов полностью построена на файловой системе и подпроцессе).

**Внешние вызовы:** запуск подпроцесса `fontforge` на каждую конвертацию (до 4, если бы путь кода был достижим); ни одного реального исходящего вызова Telegram с содержимым файла (только текстовые ответы с путями, да и то, только если бы мёртвый путь кода как-то был достигнут).

**Обработка ошибок:** `try/catch` вокруг всей последовательности на пользователя, но достижим он лишь при условии, что `generateRandomFonts` действительно вызывается, — а этого, согласно багу выше, сейчас не происходит.

**Побочные эффекты (в текущей сборке):** **отсутствуют** — `/font_generator` является живой зарегистрированной командой, которая при вызове молча ничего не делает.

## 7. Команда `/bulk_messages` (отладочный/нагрузочный инструмент)

**Триггер:** апдейт из приватного чата с текстом `/bulk_messages`. Ничто в её регистрации не отличает её от настоящей пользовательской фичи — она видна в списке команд Telegram (регистрируется тем же вызовом `setMyCommands`, что и `/start` и `/font_generator` в Потоке 1) и не требует никаких особых прав для вызова; **запустить её может любой пользователь, способный открыть приватный чат с ботом.**

**Последовательность:**
1. `BulkMessagesCommand.handle(ctx)`:
   ```ts
   const chats = [2815426, 5067823410, 858262157]; // захардкожено, предположительно тестовые chat ID разработчика
   for (let i = 0; i < 100000; i++) {
       for (const chatId of chats) {
           promises.push(this.sendRandomText(chatId));
       }
   }
   await Promise.all(promises);
   console.log("done");
   ```
   В отличие от бага в `FontGeneratorCommand`, здесь `this.sendRandomText(chatId)` **действительно вызывается** (а не привязывается через `.bind`) — этот цикл честно ставит в очередь **300 000** сообщений (`100 000 × 3` захардкоженных chat ID) настолько быстро, насколько успевает синхронный цикл.
2. `sendRandomText(chatId)`, для каждого из 300 000 вызовов:
   - `StringHelper.generateRandomString(1000)` — новая случайная строка из 1000 символов на каждый вызов (не переиспользуется на все 300 000 вызовов — 300 000 отдельных генераций строк).
   - `await FileHelper.createDirectoriesByDate("/home/sardor/applications/telegram-bot/tmp")` — **захардкоженный абсолютный путь, специфичный для машины исходного разработчика**. На любом другом хосте `FileHelper.isExist(...)` для этого пути почти наверняка вернёт `false`, так что этот вызов бросит `InvalidPath.isNotExist(...)` уже при первом обращении — **300 000 раз**, и каждый раз это необработанный reject внутри одного из 300 000 `Promise` в массиве `promises`, переданном в `Promise.all`. Отметим, что результат создания директории **нигде не используется** — возвращаемое значение отбрасывается, — так что даже там, где путь существовал бы, этот вызов был бы чистыми накладными расходами (300 000 избыточных обращений к файловой системе), никак не влияющими ни на содержимое сообщения, ни на доставку. Этот побочный вызов вообще не имеет отношения к конвертации шрифтов, хотя внешне и напоминает паттерн из `FontConvertor`/`FontGeneratorCommand`.
   - Поскольку `Promise.all` **реджектится сразу, как только реджектится любой из входных промисов**, а первый же вызов `sendRandomText`, дошедший до броска в `createDirectoriesByDate`, сделает это практически мгновенно, **`Promise.all(promises)` на практике реджектится почти сразу на любой машине, кроме машины исходного разработчика** — задолго до того, как выполнится большинство из 300 000 вызовов `planner.push(...)`, расположенных дальше в теле функции (JS выполняет каждый `async`-вызов до первого `await`, немедленно упирается в `await FileHelper.createDirectoriesByDate(...)`, и лишь те вызовы, которым удалось разрешиться, идут дальше определять `handler` и вызывать `planner.push`). То есть практический радиус поражения от вызова этой команды на хосте, отличном от машины исходного разработчика, меньше, чем «всегда ставит в очередь 300 тысяч сообщений»: многие отдельные вызовы `sendRandomText` падают на проверке директории, не доходя до `planner.push`. Хотя, в зависимости от планирования микрозадач в Node, заметное их число всё же может успеть стартовать (и положить сообщения в `Planner`) в том же тике, прежде чем `Promise.all` увидит первый reject.
   - Для любого вызова, который *всё же* прошёл проверку директории (например, если этот путь существует, или на машине самого разработчика): строится замыкание `handler`, вызывающее `bot.grammy.api.sendMessage(chatId, randomText)` — обратите внимание, здесь используется **`bot.grammy.api`**, синглтон уровня бота, а **не** `ctx.api`. Значит, эта отправка ограничивается по скорости только потому, что вручную направляется через `planner.push({..., callback: handler, priorityOnError: PRIORITY.MEDIUM}, PRIORITY.LOW)` (см. замечание «Область действия» в Потоке 4), а не через автоматический перехват `ctx.api`.
3. Собственного `try/catch` у обработчика команды нет — в `handle()` нет `try` вокруг `await Promise.all(promises)`; если тот реджектится (почти неизбежный исход, см. выше), reject без защиты всплывает к границе обработки ошибок grammY ровно так же, как любая другая ошибка пайплайна (терминальный путь ошибок из Потока 3), а `console.log("done")` не выполняется никогда.

**Условия/ветвления:** отсутствуют — три захардкоженных chat ID, безусловный цикл.

**Изменения состояния:** до 300 000 записей, поставленных в корзину `LOW` в `Planner` (с оговоркой про сбой проверки директории выше); `Planner.managers` получает до 3 новых записей `SlotManager` (по одной на захардкоженный `chatId`, если их там ещё нет от другой активности) — навсегда, в силу проблемы неочищаемой `Map` (`docs/architecture.md` §6, issue [#32](https://github.com/yuldashevsardor/telegram-bot/issues/32)).

**Обращения к хранилищу:** напрямую отсутствуют (сама команда к Postgres не обращается — хотя upsert'ы сессии/пользователя окружающим пайплайном для самого апдейта `/bulk_messages` происходят, как и для любой команды).

**Внешние вызовы:** до 300 000 вызовов `sendMessage` в три конкретных chat ID, которые почти наверняка не являются чатом вызвавшего пользователя, — **любой пользователь, обнаруживший и запустивший эту команду, может заставить бота попытаться завалить три произвольных захардкоженных чата Telegram сообщениями числом до 300 000 на каждый**; это по-настоящему запускаемый пользователем вектор злоупотребления, а не просто инертный мёртвый код, в отличие от бага в `FontGeneratorCommand`. (Дойдёт ли это до Telegram в сколько-нибудь значимом масштабе, зависит от того, случится ли на развёрнутом хосте описанный выше сбой проверки директории, — но это случайность текущего захардкоженного пути, а не защита.)

**Обработка ошибок:** осмысленной нет — самый вероятный исход в реальном мире это необработанный reject `Promise.all`, досрочно завершающий весь обработчик без какой-либо очистки того подмножества из 300 000 отправок, которое уже успело попасть в `Planner` до того, как reject был замечен (эти поставленные в очередь сообщения остаются в очереди и со временем всё равно будут обработаны `Broker`'ом).

**Побочные эффекты:** как описано выше — это самый «взрывоопасный» живой путь кода во всём приложении, зарегистрированный как обычная, недокументированная команда бота без аутентификации.

## 8. Bootstrap i18n / локалей Fluent

**Триггер:** часть `Bot.setup()` (Поток 1, шаг 4), выполняется ровно один раз за время жизни процесса, до того как бот начнёт принимать апдейты.

**Последовательность:**
1. `FileHelper.findFilesByExtensions(path.join(rootDir, "src", "infrastructure", "bot"), [".ftl"])` — рекурсивно ищет (через `tiny-glob`, шаблон `**/*.{ftl}`) файлы `.ftl` в дереве скомпилированного/запущенного `src/infrastructure/bot`. Сейчас находит ровно один файл.
2. Для каждого найденного пути строка разбивается по `.`, и предпоследний сегмент берётся как локаль (например, `start.conversation.locale.ru.ftl` → `["start","conversation","locale","ru","ftl"]` → индекс `length-2` → `"ru"`). **Это чисто конвенциональный парсер имени файла без какой-либо валидации** — файл вида `foo.bar.ftl` (одна точка перед расширением) дал бы локаль `"bar"`, а файл вообще без сегмента локали (например, `foo.ftl`) дал бы фиктивную «локаль» `"foo"`. Сегодня это не задействовано (существует один-единственный корректно названный файл), но это реальная хрупкость, если новые `.ftl` будут добавляться без строгого соблюдения соглашения `*.locale.<lang>.ftl`.
3. Файлы группируются по разобранной локали; для каждой группы вызывается `fluent.addTranslation({ locales: locale, filePath: files, isDefault: true })`, регистрирующий ключи этих файлов в `@moebius/fluent`.
4. `useFluent({ fluent, defaultLocale: "ru", localeNegotiator: () => "ru" })` устанавливается как middleware grammY (шаг 8 пайплайна из Потока 3). **Негоциатор полностью игнорирует свой аргумент `ctx`** — ни проверки `ctx.from.language_code`, ни поиска предпочтений на пользователя/чат: каждый апдейт от каждого пользователя разрешается в `"ru"`.

**Условия/ветвления:** ничего, кроме описанного выше соглашения о разборе локали.

**Изменения состояния:** отсутствуют (набор переводов Fluent строится один раз при старте и далее не изменяется).

**Обращения к хранилищу:** отсутствуют.

**Внешние вызовы:** отсутствуют (только локальное чтение файлов).

**Обработка ошибок:** `findFilesByExtensions` бросает исключение, если ему передали пустой массив расширений (здесь неприменимо, `[".ftl"]` захардкожен); другой обработки нет. Если бы разбор файла `.ftl` когда-нибудь упал (некорректный синтаксис Fluent), это проявилось бы так, как это делает `addTranslation` из `@moebius/fluent` на плохом вводе, — здесь ошибка не перехватывается, что прервало бы `Bot.setup()` и попало бы во внешний catch в `Bot.run()` (лог critical, бот в итоге фактически не работает — см. Поток 1).

**Побочные эффекты:** отсутствуют, кроме реестра Fluent в памяти.

## 9. Логирование и корреляция запросов (сквозной аспект)

Это не самостоятельно запускаемый поток, но на него ссылается почти каждый поток выше — здесь он для полноты описан один раз.

**Какой конкретный логгер стоит за каждым внедрением `@inject<Logger>(Infrastructure.Logger)`**, решается один раз, при настройке контейнера (Поток 1), на основе `config.logger.default` (env `LOGGER_DEFAULT`, по умолчанию `PinoLogger` в production / `ConsoleLogger` в разработке). Оба конкретных логгера фильтруют по `levels` (env `LOGGER_LEVELS`, по умолчанию `WARNING/ERROR/CRITICAL` в production или все уровни в разработке) — вызов логирования ниже настроенного уровня ничего не делает (сообщение не форматируется и не пишется).

**Когда активен `PinoLogger`,** каждый доступ к свойству внедрённого `Logger` (он привязан как `Proxy`, см. `docs/architecture.md` §4) заново выполняет две вещи на **каждом отдельном вызове**, а не только на первом: (1) проверяет `asyncLocalStorage.getStore()?.get("logger")` и подставляет этот дочерний логгер запроса вместо общего синглтона, если он есть (то есть внутри области `asyncLocalStorage.run(...)` из `AsyncLocalStorageMiddleware` — см. шаг 4 Потока 3 — каждый вызов логирования прозрачно получает дочерний логгер, помеченный `requestId`, а не голый синглтон); (2) снова вызывает `target.setLevels(config.logger.levels)` на выбранной цели, прежде чем передать дальше собственно доступ к свойству. Благодаря этому только что созданный дочерний логгер (из `PinoLogger.child()`, который **не** наследует `levels` от родителя — поле `levels` в `AbstractLogger` при конструировании по умолчанию `[]`) всё равно работает корректно: Proxy заново применяет настроенные уровни при каждом обращении перед использованием — реальный, пусть и неочевидный, самовосстанавливающийся механизм, а заодно небольшая повторяющаяся работа на каждую записанную строку лога.

**Когда активен `ConsoleLogger`** (дефолт для разработки), `AsyncLocalStorageMiddleware` это обнаруживает (`!(logger instanceof PinoLogger)`) и полностью пропускает настройку корреляции — каждая строка лога от каждого параллельно обрабатываемого апдейта выглядит одинаково с точки зрения идентичности запроса; сопоставить строки логов с конкретным апдейтом/запросом в этом режиме невозможно.
